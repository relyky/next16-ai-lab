# 餅圖的扇形顏色以 colorKey 指向資料欄位

讓 AI 為餅圖指定顏色時，發現顏色的**層級**與笛卡兒圖不同：折線／長條／區域圖是「每組數列一色」，顏色因此自然掛在 `series[].color` 上；餅圖是「每個扇形一色」，而扇形的數量由資料筆數決定。我們新增選填的 `colorKey`，指向 `data` 內存放色碼的欄位，與餅圖既有的 `nameKey` / `valueKey` 同層級。

在此之前，餅圖的扇形顏色**只有預設配色這一條路徑**——沒有任何覆寫機制。這也是為什麼調色盤還是純灰時，餅圖是四種圖表中唯一完全無法補救的一種。

## 被否決的替代方案

**讓餅圖沿用 `series` 結構**，以一組數列承載顏色。表面上最省事：schema 不必長出新欄位，前端也少一條分支。

否決的理由與 ADR 0001 是同一條——**型別會說謊**。一組數列只有一個 `color`，裝不下 N 個扇形的顏色。要硬塞，只剩兩種寫法：讓 `color` 變成陣列（那它就不再是「數列的顏色」，只是借了 `series` 的殼放一個平行陣列），或要求 AI 傳 N 組各含一個顏色的數列（那 `series` 的語意從「數列」被偷換成「扇形」，且它的 1~6 組上限與餅圖的資料筆數上限 100 直接矛盾）。

兩種寫法都是把餅圖的真實約束推出型別系統之外，靠註解與執行期檢查維持。ADR 0001 正是為了不讓餅圖借用笛卡兒圖的形狀而存在，此處再借一次會直接抵銷那次重構。

**另一個被否決的方案是讓 AI 傳一個與 `data` 等長的顏色陣列**（如 `colors: string[]`）。它避開了 `series` 的語意偷換，但引入一個新問題：顏色與資料的對應關係靠**位置**維持，AI 少傳一個、多傳一個，或在 `data` 中途插入一列，整張圖的配色就靜默錯位——而錯位的圖看起來完全正常，沒有任何跡象可供察覺。`colorKey` 把對應關係放進資料列本身，色碼與它所屬的類別同進同出，這種錯位在結構上就不可能發生。

## 為什麼是 `*Key` 而不是新的慣例

餅圖已有 `nameKey` 與 `valueKey` 兩個「指向 `data` 內欄位」的欄位，`colorKey` 完全貼齊這個既有風格。MCP 層的契約因此保持一致：三個 `*Key` 是同一種東西，AI 只需要學一次。

前端再各自映射到 recharts 的真實著色點——笛卡兒圖映到 `stroke` / `fill`，餅圖映到扇形的 `fill`。**契約一致不代表實作共用**，這與 ADR 0001 的立場相同。

色碼沿用數列顏色同一套 hex 約束，不另立規則。資料欄位的值型別本來就接受字串，圖表定義的 round-trip 因此不需要放寬任何 schema。

## 影響

**未指定的列回退預設配色，且回退取該扇形自己的序號。** 混合案例（有些扇形指定、有些沒有）是刻意支援的，不是邊界。序號若取「第幾個未指定」，每個扇形的預設色會隨前面幾列有沒有指定色而漂移——同一份資料只改一格顏色，其餘扇形全部換色。

**`colorKey` 的存在性須以全列的欄位聯集判定。** `nameKey` / `valueKey` 每一列都必須有值，看 `data[0]` 就夠；`colorKey` 不同——「第 1 列剛好沒有色碼欄位」正是上述混合案例中最自然的寫法之一，只看 `data[0]` 會把它誤判成欄位不存在而擋下。兩者的檢查方式不同不是疏漏，是語意本來就不同。

**schema 開了，AI 未必會用。** 選填欄位的說明只存在於巢狀 JSON Schema 的 property description 裡，AI 讀不讀得到、會不會主動使用，是另一回事。故四個 chart tool 的**描述**都必須明文寫出配色方式（笛卡兒圖用數列顏色、餅圖用 `colorKey`，未提供時前端套用預設配色）。這與 ADR 0001 之後 `stacked` 的處境是同一個問題：選填欄位不會在 JSON Schema 產生 `default`，描述是它唯一的落點。
