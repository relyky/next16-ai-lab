# 圖表定義採 discriminated union

新增餅圖時，發現它與既有的折線／長條／區域圖在資料形狀上本質不同：既有三者是「類別軸 × 多數列」，餅圖是「單一數列 × 多類別」。我們把圖表定義從「單一 object 加上 type 欄位」改為以 `type` 為判別子的 discriminated union，讓兩種形狀各自擁有精確的型別，前端渲染時可藉型別收窄取得正確欄位。

## 被否決的替代方案

**讓餅圖沿用共用 schema**：以 `xKey` 充當類別名稱欄位、`series` 限定恰好一組。改動明顯較小——不必動 union、型別、擷取邏輯。

否決的理由是**型別會說謊**：`series` 的 schema 宣稱可有 1~6 組，而餅圖的真實約束是恰好一組，這個落差只能靠執行期檢查與註解維持，型別系統幫不上忙。`xKey` 在餅圖語意上其實是 `nameKey`，名稱錯位還會一路帶到前端。

換句話說，該方案是把成本從編譯期推遲到執行期。既然 scatter、radar 未來同樣不吃現行形狀，這筆重構遲早要付，在只有四種圖表類型時付最便宜。

## 影響

新增圖表類型的模式因此固定下來：**一個 union 分支 + 一個渲染子元件**。圖表卡片元件相應拆為三層——外框（邊框與標題）、依 `type` 的分派（同時是型別收窄點）、各類型的子元件。

代價是圖表卡片不再能用單一張對照表涵蓋所有類型。這是刻意的：型別收窄後，笛卡兒圖與餅圖兩段渲染程式的變數互不相通，強行統一只會共用作用域而無法共用任何實質邏輯。
