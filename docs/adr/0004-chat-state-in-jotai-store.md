# 對話狀態移入 Jotai 的預設 store

對話頁的狀態原本全部住在 `ChatPage` 的 `useState` 裡。使用者聊到一半切到「首頁」或「關於」，元件卸載，整段對話就沒了——切回來面對的是一個空白的對話頁，先前的訊息、sessionId、累計用量一併消失，只能重問一次。

把這五項狀態（訊息陣列、sessionId、模型、累計用量、串流中與否）移到 Jotai 的**預設 store**，並把送出邏輯搬成 write-only atom。預設 store 是 module-scope 的 singleton，生命週期正好是「一個分頁」：切頁不重建，重新整理才重建——與需求逐字吻合。

刻意**不包 Provider**。root layout 是 Server Component，包 Provider 還得額外做一個 client 包裝元件，而預設 store 已經提供了要的生命週期，換不到任何東西。

## 被否決的替代方案

**用 React Context 而非 Jotai。** 不需要新依賴，且專案已有既存的 Context 先例（`ChartPaletteProvider`）。決定性的理由是專案定位：這是 AI 實驗室專案，引入並熟悉 Jotai 本身有價值；加上 write-only atom 讓送出邏輯離開元件時比 Context 版乾淨——邏輯直接住在 store，不必為了「讓它活過卸載」而繞過 React 的生命週期。

代價要說清楚：**測試隔離需要顯式的全域 reset**。Context 版靠元件卸載自動達成，Jotai 版不會（見下方「影響」）。這是這次選擇實際付出的成本。

**用 localStorage / sessionStorage 持久化。** sessionId 只在伺服器本機的 SDK session 中有意義，重啟 dev server 或換一台機器就失效。持久化訊息卻無法持久化 session，會產生「訊息在但續談斷掉」的假象——使用者看到完整的對話歷史，追問卻得到一個不記得脈絡的助手。那比全部清空更難理解。

**切頁時中止串流。** 表面上是該做的 cleanup，實際上有兩個問題。其一，中止會在回覆上留下「（已中斷）」——使用者從沒按過中斷鈕，那則提示是在說謊。其二，中止前端請求不必然停下伺服器端的生成，token 大概率照樣消耗，中止只是主動放棄已付費的結果。故刻意不加任何卸載時的 cleanup，並在程式碼註解寫明，否則後人會當成漏掉的 cleanup 而「修好」它。

**把「顯示處理過程」一併提升。** 它的既有註解已明訂為「純顯示濾鏡，刻意不做持久化」。它不是對話的一部分，是「我現在想不想看」。提升它會是一次未被要求的語意變更，故留在頁面，切頁後回到預設的關閉。

## 影響

**session 的邊界由頁面變成分頁。** CONTEXT.md 的「使用者心智的 session」定義隨之改寫。「累計用量」段落引用這個詞來定義自己的邊界，定義改了那裡自動跟著對，不需要修改——這正是 glossary 有價值的證據。

**module-scope 的 atom 不隨元件卸載消滅，測試須顯式 reset。** 這是本決策最容易踩的坑，實作過程中確實踩到了：atom 的值住在 store，RTL 的 `cleanup()` 只卸載元件，上一個測試的訊息與 sessionId 會整批殘留到下一個測試。至少三處既有測試會直接失敗——斷言「第一次送出前不顯示模型與 session 資訊」、斷言「第一次請求不帶 sessionId」，以及各種空狀態與開關預設值的斷言。

解法是在測試設定檔的既有 `afterEach` 掛一次全域 reset。範圍限定在檔案內：vitest 預設每個測試**檔案**有獨立的 module registry，這是檔案內跨測試的污染，不跨檔案。相較於「把 45 處 `render` 都包一層 Provider」，改動量差距懸殊。

store 模組因此匯出一份**具名的「atom／初始值」清單**供 reset 迭代，讓「新增了 atom 卻忘記 reset」變成看得見的疏漏，而不是只在特定測試執行順序下重現的偶發污染。reset 一併歸零 message id 計數器與 abort controller——它們同樣是 module-scope，同樣不隨卸載消滅。

**「以 messages 長度產生 id」的做法不再成立。** 原本 id 由目前訊息陣列的長度推算，能運作是因為每輪剛好新增兩則、長度恆為偶數。送出邏輯離開元件後，閉包裡的陣列不再隨渲染更新，每輪都會算出同樣的 0 和 1——React key 重複，且「就地更新助手訊息」的 id 比對會命中上一輪的舊訊息並把它覆寫掉。改為模組層級的單調遞增計數器，與對話狀態同層。

**串流中與否必須跟串流同層。** 它若留在頁面：使用者在串流中切走，store 裡的串流繼續跑；切回來時頁面重新掛載，它是全新的「否」，輸入框顯示「送出」且為啟用狀態。使用者可以再送一則，兩個串流同時寫訊息陣列，而 abort controller 被後者覆寫——前一個永久洩漏、再也無法中斷。這不是理論競態，是必然發生的。

**送出邏輯需要防重入。** 現況沒有防護，是因為 loading 與送出鈕同在一個元件裡、不可能不同步；狀態提升後這個保證消失（切頁往返是新的入口）。這是 abort controller 被覆寫而洩漏的最後一道防線。

**abort controller 不做成 atom。** 它不是渲染會用到的值，沒有任何元件需要因它變動而重繪，放進 atom 只會多一層無意義的訂閱。
