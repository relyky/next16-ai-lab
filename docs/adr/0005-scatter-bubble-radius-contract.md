# 散佈圖的氣泡大小契約收半徑而非面積

散佈圖的 `sizeKey` 把第三個維度映射成氣泡的大小。recharts 表達這件事的原生方式是 `ZAxis.range`，而它的單位是**面積**——內部以 `radius = sqrt(size / π)` 反推半徑。我們的 tool 契約不沿用這個單位，改收 `[最小半徑, 最大半徑]`（單位 px），半徑由前端一個具名純函式 `bubbleRadiusAt` 依資料值算出。

面積在**感知上**有它的道理——人眼比較圓的大小時比較的是面積，不是半徑；照半徑線性映射會讓大值看起來被過度放大。這一點我們並不推翻（見下節的折衷）。問題出在**數字對呼叫端的可讀性**：`[64, 400]` 換算成半徑是 4.5px 到 11.3px，光看那兩個數字，沒有人猜得出畫出來的點會是多大。LLM 要嘛不敢動這個參數，要嘛傳一個量級完全錯誤的值。

契約收半徑，LLM 拿到的是它直覺會用對的單位（「這張圖的點最大 20px」是可以直接想像的），而易錯的映射換算被鎖在前端一個具名、單獨測試過的純函式裡——只有一處會錯，而且那一處有測試守著。

## 被否決的替代方案

**前端寫死一組常數，完全不開放 `range`。** 它更 MVP：schema 少一個欄位、少三條驗證、tool 描述也短一截。

否決的理由是**合適的氣泡範圍與資料的離散程度有關**。點密集時需要小氣泡，否則整張圖糊成一片；點稀疏時可以放大，否則畫面空曠、第三個維度的差異看不出來。寫死一組常數必然會讓其中一種資料集畫出難讀的圖，而那正是散佈圖最有價值的使用情境。開放 `range` 加上前端預設能同時滿足兩者：LLM 不管時有合理的預設，需要調整時調得動。

**另一個被否決的方案是讓 LLM 直接傳 recharts 的面積值。** 它最省事——前端連換算函式都不必寫，參數原樣往下傳。但那等於把 recharts 的內部實作細節洩漏成我們的對外契約：換掉圖表函式庫時契約就得跟著改，而已經產生的圖表定義會全部失效。更直接的代價是上一節說的可讀性——把一個反直覺的單位交給呼叫端，換得前端少寫五行。

## 映射曲線：0.75 次方的折衷

契約收半徑，但「半徑怎麼隨資料值變化」是另一個問題。原本的作法是把半徑範圍換算成面積交給 recharts 的 `ZAxis.range`，讓它線性映射到面積後再開根號還原半徑——也就是**面積線性**（半徑 ∝ 值的 0.5 次方）。這在多數真實資料下讀不出差異：`sqrt` 把中段往高值推，20 筆資料、`range: [6, 40]` 的實測半徑是 `26.1, 27.0, … 39.4, 40.0`，第三個維度等於白做。

兩個極端各有各的道理，且互相衝突：

- **半徑線性**（指數 1）契約最誠實——`range` 說 6–30 就均勻畫 6–30，數字與畫面對得上——但放棄了「面積在感知上正確」這件事。人眼比較圓的大小時比較的是面積，半徑線性會讓大值看起來被過度放大。
- **面積線性**（指數 0.5）感知正確，但中段被壓縮，且契約的數字與畫面對不上。

取 **0.75 次方**，兩邊各讓一步：中段不再擠在高值區，感知上的放大也不像半徑線性那麼激進。以 size `[0, 50, 100]`、`range [6, 30]` 為例，中間值落在 **20.27**，而面積線性會是 22.97、半徑線性會是 18.00。

（上文引述的實測數字用的是修正前的 `range: [6, 40]`——那是缺陷被量到時的條件，故照原樣保留；40 在本次改動後已超出上限。）

沒有一個客觀正確的指數——這是一個取捨點，記錄下來是為了讓未來想調整的人知道兩端各會失去什麼。

## 起算點是資料最小值，而非 0

recharts 的內建映射把 `[0, dataMax]` 映到 `range`，起點固定為 0。這表示只有資料**恰好含 0** 時最小半徑才取得到：size 從 10 起算、`range: [6, 40]` 時，最小的氣泡實測是 13.87 而非契約宣稱的 6。「最小半徑」這個契約詞對大多數資料集因此是說謊的。

修正為先把值正規化到 `[dataMin, dataMax] → [0, 1]` 再套曲線，`range` 的兩端恆等於資料的兩端。

**代價是不能再用 `ZAxis.range`**：曲線與起算點都寫死在 recharts 內部。半徑改由前端一個具名純函式 `bubbleRadiusAt` 算出，再經自訂的 `shape` 畫出。`ZAxis` 仍保留，但只承載 Tooltip 需要的 `name` 與 `unit`，不再參與幾何——這一點在程式碼裡有註解說明，否則讀者會以為半徑仍是它算的。

**資料值全部相同時取最小半徑。** 此時沒有可分辨的大小差異；取最大半徑會讓一組毫無差異的資料畫出滿版的氣泡，暗示了不存在的高值。

## 上限與預設值的由來

**最大半徑上限 30。** 圖表容器高度固定，繪圖區約 180–200px。原訂 40（直徑 80px）實測在 20 筆資料下氣泡會互相吞沒、糊成一片；30 仍足以表達差異而不至於蓋掉鄰近的點。這與既有的資料列數上限 100、數列數上限 6 是同一種東西——不是技術限制，而是避免 LLM 產生過大的值拖垮圖表可讀性。

由 40 降為 30 會讓既有的 `range: [6, 40]` 這類呼叫變成驗證錯誤，屬預期行為：錯誤訊息帶出新上限，LLM 讀得到也改得動。

**預設 `[4, 12]` 維持不變。** 它是未提供 `range` 時的保守預設，畫出來的圖與不特別設定 `ZAxis` 的 recharts 散佈圖看起來相當，本來就不是上述兩個缺陷的來源。

**兩個半徑都須為正。** 半徑 0 或負數畫不出可見的氣泡；這一條在 schema 層即以 `positive()` 擋下，不必等到執行期。

**檢查 `range[0] < range[1]`。** 傳反了會畫出「大值畫小、小值畫大」——一張看起來完全正常但語意完全相反的圖。這種錯誤沒有任何視覺跡象可供察覺，只能在驗證階段擋下。

## `range` 選填而非必填

`sizeKey` 本身已是選填。若 `range` 必填，會出現「有 `range` 沒 `sizeKey`」這種無意義的必填組合——呼叫端被迫為一個自己沒打算用的功能傳參數。兩者都選填，加上前端預設，是唯一不產生無意義組合的設計。

## 有 `range` 無 `sizeKey` 回報錯誤，而非靜默忽略

傳了 `range` 卻沒傳 `sizeKey` 時，`range` 沒有可映射的欄位。此時回報錯誤，與既有 schema 對未知欄位「明確拒絕而非靜默忽略後畫出一張參數對不上的圖」的立場一致（見 ADR 0001 之後各圖採 `strictObject` 的理由）。

靜默忽略在這裡格外有害：LLM 會以為自己成功調整了氣泡大小，而畫面上所有點一樣大。它拿不到任何訊號，也就不會重試。

## 影響

**契約的單位語意難以逆轉。** 改成面積會讓所有既有的圖表定義失效——同一組數字在兩種單位下相差一個平方與 π。這正是它值得記錄的原因：未來讀者看到 `bubbleRadiusAt` 時第一個問題會是「為什麼不直接讓 LLM 傳 recharts 的 `range`？」，本文件就是那個問題的答案。

**換算函式必須單獨測試。** jsdom 不產生 SVG 幾何，曲線指數與起算點兩個易錯點在渲染斷言中驗不到。故 `bubbleRadiusAt` 匯出為純函式並自帶測試，涵蓋兩個端點、中段、預設值與「資料值全部相同」的退化案例。

**只測兩端點的測試抓不到壓縮現象。** 面積線性下兩端點也是對的，錯的是中段——這正是缺陷能存活到 issue #69 才被發現的原因。渲染層因此另有一條「均勻分布的資料，中段氣泡不擠在高值區」的測試。

**上限與預設值只定義一次。** 兩者同時出現在 schema 的 describe、執行期檢查、tool 描述與前端換算四處。散成字面值會在改動時漏改，而 tool 描述正是這條契約對 LLM 唯一可見的落點——描述說 40、檢查擋在 30，LLM 會反覆撞上一道它讀不到的牆。故 `MAX_BUBBLE_RADIUS` 與 `DEFAULT_BUBBLE_RADIUS_RANGE` 定義於 `chart-tool.ts` 並由其餘三處引用。

**`sizeKey` 與 `range` 的用法必須寫進 tool 的描述。** 選填欄位的說明只存在於巢狀 JSON Schema 的 property description 裡，LLM 未必讀得到——ADR 0003 已記錄這個問題。氣泡大小是散佈圖相對於其他圖表最有價值的部分，若 LLM 從不主動使用，等於沒做。
