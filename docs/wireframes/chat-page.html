Chat Page Wireframe

「對話」頁（/chat）線框圖設計文件 — 我的財務助手

來源：src/app/chat/page.tsx

1. 版面骨架

整頁由 layout 提供外框：固定高度的導覽列，加上吸收剩餘高度的內容區。Chat 頁自身是一個置中的單欄，欄內由上到下分三段。三段之中只有訊息列表會長高，它把底部區塊推到視窗底；訊息不足一頁時底部區塊仍貼齊視窗底部，不會浮在半空。

各區塊的責任

區塊元件負責什麼
導覽列NavBar（layout 提供）站台層級的頁面切換，標示當前頁。Chat 頁不介入
內容欄ChatPage限制閱讀寬度並置中，持有本頁全部狀態（訊息、session、用量、載入中）
① 工具列Switch切換工具歷程的顯示與否。純顯示濾鏡，不影響資料收集
② 訊息列表UserMessage／AssistantMessage依序渲染對話。唯一會長高的區段——它吸收剩餘高度，才能把底部區塊壓在視窗底
③ 底部區塊ChatPage 內的 wrapper以 sticky 把 ③a 與 ③b 一起釘在視窗底並遮擋捲動內容。釘底責任刻意放在這一層而非輸入列——否則用量列會被留在上面隨內容捲走
③a 用量列UsageLine顯示本輪 session 的累計用量。尚無用量時整行不存在（見 §5）
③b 輸入列ChatInput接收輸入、送出與中斷。自身不管釘底

2. 訊息泡泡結構

兩種角色採不同的視覺語言：使用者為右側實心色塊，助手為左側白底卡片。助手的一則回應會長出三種產物——泡泡、圖表、提示——依串流事件動態出現，彼此並列為兄弟而非巢狀：圖表若放進泡泡內，卡片底色會疊在同樣的卡片底色上，內框沒有對比、只剩雜訊。三者再以一層淡底色的群組（assistant-turn）收成一則，補回並列後失去的歸屬感。

群組底色在深色模式必須另外指定。本專案的卡片底色比頁面底色更亮——卡片是浮起的。若深色模式沿用與淺色相同的次要底色，群組會比卡片還亮，卡片反而凹陷，深度線索與淺色模式相反（實測圖表卡對比僅 1.01，幾乎沒入背景）。故深色模式改用比卡片更暗的薄層，兩種模式下卡片都比群組底色亮。

區塊出現規則

區塊出現條件設計理由
泡泡本身已有工具歷程或文字圖表可能比文字先到，此時泡泡尚無任何內容——不留一個只有外框的空卡片
Ⓐ 工具歷程已有工具呼叫，且開關為開排在文字之前，反映「先呼叫工具、再依結果作答」的實際流程
Ⓑ 文字已有文字文字尚無內容時不留空白區塊。助手回覆以 markdown 渲染（支援中日韓排版、程式碼、數學式；不支援圖表語法——本頁圖表走 Ⓒ 的圖表卡）。只有正在串流的那一則帶逐字淡入，否則每問一個新問題整段歷史都會重播閃動。使用者訊息刻意不走 markdown——使用者打字通常不是 markdown，渲染會吃掉 1. ／- ／# 開頭的字面輸入
Ⓒ 圖表本則有圖表依產生順序排列；已移出泡泡與其並列，各自保有單層外框。與泡泡不同，圖表欄必須撐滿群組寬度——圖表是依父層實際寬度繪製的，父層若隨內容縮放就量不到寬度、圖畫不出來。餅圖的扇形直接標出類別名稱與佔比：扇形角度雖然就是佔比，但「看起來比較大」讀不出數字，而截圖、列印、觸控裝置都沒有 hover 可看提示框；過小的扇形不標，標籤會互相疊住反而更難讀
Ⓓ 提示該輪被中斷或失敗排在所有內容之後：使用者要讀完已浮現的內容才看到「已中斷」。刻意不併進回覆文字——回覆停在未閉合的程式碼區塊時，併進去的提示會被一起吞進程式碼框裡

3. 工具歷程列狀態

這一列的責任是讓使用者理解處理過程，而非提供除錯用的完整記錄：只顯示工具名稱與狀態，不含呼叫參數與回傳內容。名稱以原始全名呈現、不做前綴剝除或美化——使用者看到的與日誌裡的是同一個字串，回報問題時才對得起來。

4. 輸入列兩態

輸入列只有兩種樣態，由「是否正在串流回覆」決定：串流中不能再送出，但必須能中斷，故送出鈕原地換成中斷鈕。輸入框隨內容長高，但有高度上限，超過改為框內捲動——輸入框無限長高會把訊息列表整個擠出畫面。

5. 用量累計列

完成一輪問答後，輸入列正上方出現一行灰色小字，顯示這一輪 session 的累計 token 用量。第一輪完成前不顯示，重新整理歸零。四項分開呈現、不做總和 —— 四者計價完全不同（cache_r 約為 in 的 1/10、cache_c 約 1.25 倍），且三種輸入分類互斥，相加成單一「總 token 數」在財務意義上會誤導。

四個標籤（in／cache_c／cache_r／out）沿用 Anthropic 生態圈慣例。注意 in 的實際語意是「未命中快取的輸入」而非「總輸入」——此頁受眾為開發者，若日後改給非開發者看，標籤應重新檢討。

累加規則

情境行為設計理由
正常完成的輪次計入該輪結束前，後端會回報這一輪的用量
失敗的輪次（次數用盡、服務過載）計入那些 token 確實已消耗，漏掉會低報。用量必須搶在錯誤之前回報——前端一收到錯誤就停止解析，排在後面會被漏接
中斷的輪次不計入，且不特別標示中斷時該輪不會產生結算訊息，用量無從取得。那些 token 實際上已消耗，但估算會是編造的；代價是顯示數字略低於實際帳單
對話在後端被分支不歸零使用者看到的是同一個對話視窗、同一串訊息；分支是後端的實作細節，不該漏到畫面上
重新整理歸零累計只存在於這個分頁，「這一輪 session」＝「我打開這頁到現在」

累加刻意由前端負責：後端每次請求各自獨立、維持無狀態，前端本來就持有整段對話，天然是這一輪 session 的邊界持有者。詞彙定義見 CONTEXT.md。

6. 頁面狀態流

頁面共四種可見狀態，由「有沒有訊息」「是否正在串流」與該輪的結束方式共同決定。

圖表配色的分配規則

色序不是依數列序號循環，而是依類別名稱查一份對照表：查的鍵就是讀者在圖例上看到的那個名稱。同名即同色，因此「銷售部」在折線圖與餅圖裡是同一個顏色，讀者不必在兩張圖之間重新對照圖例。

對照表的範圍是整段對話的所有圖表，而非單一訊息——跨訊息的兩張圖也共用同一份色序。色序取「首次出現順序」；對照表由當前的圖表清單推導而得，不是邊畫邊累積寫入的，因此串流過程中畫面反覆更新也不會讓顏色漂移。明度刻意深淺交錯而非由深到淺排列，相鄰兩個數列才有足夠對比。

8. 互動與無障礙備註

  • 顯示處理過程開關：預設關閉——工具歷程是輔助資訊，不是每次對話都要看的內容，預設開啟會讓每則回應頂端都多出一段雜訊。它是純顯示濾鏡：關閉期間歷程照常收集，重新開啟後完整可見。刻意不記住選擇，重新整理即回到關閉。
  • 鍵盤：Enter 送出、Shift+Enter 換行；輸入法組字中的 Enter 為選字，不可誤觸送出。
  • 狀態圖示：三種狀態皆有文字標籤供輔助技術朗讀（進行中／成功／失敗），不單靠顏色傳達語意。
  • 訊息語意：使用者與助手以位置（左／右）＋色塊／卡片雙重區分，非僅靠顏色。
  • 用量數字：顯示千分位（如 11,604），長數字才讀得出量級。
