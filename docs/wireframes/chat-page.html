2. 訊息泡泡結構

兩種角色採不同的視覺語言：使用者為右側實心色塊，助手為左側白底卡片。助手卡片是容器，內部依串流事件動態長出三個可選區塊。

3. 工具歷程列狀態

ToolUsageList 只顯示工具全名與狀態，不含參數與回傳內容 — 目的是讓使用者理解處理過程，而非提供除錯 trace。名稱以原始全名呈現，不做前綴剝除。

4. 輸入列兩態

ChatInput 以 disabled（＝回覆串流中）切換兩種樣態。Textarea 為自動長高，上限 max-h-40；Enter 送出、Shift+Enter 換行，輸入法組字中的 Enter 不觸發送出。

5. 用量累計列

完成一輪問答後，輸入列正上方出現一行灰色小字，顯示這一輪 session 的累計 token 用量。第一輪完成前不顯示，重新整理歸零。四項分開呈現、不做總和 —— 四者計價完全不同（cache_r 約為 in 的 1/10、cache_c 約 1.25 倍），且三種輸入分類互斥，相加成單一「總 token 數」在財務意義上會誤導。

四種 token 分類

標籤沿用 Anthropic 生態圈慣例。注意 in 的實際語意是「未命中快取的輸入」而非「總輸入」 —— 此頁受眾為開發者，若日後改給非開發者看，標籤應重新檢討。

累加規則

情境行為設計理由
正常完成的輪次計入後端在 done 之前送 usage 事件
失敗的輪次（turn 用盡、API 過載）計入那些 token 確實已消耗，漏掉會低報。後端把 usage 排在 error 之前送出 —— 前端一收到 error 就中止解析，排在後面會被漏接
中斷的輪次不計入，且不特別標示query() 被 abort 時 result 訊息不會產生，用量無從取得。那些 token 實際上已消耗，但估算會是編造的；代價是顯示數字略低於實際帳單
sessionId 變更（fork）不歸零使用者看到的是同一個對話視窗、同一串訊息；fork 是 SDK 的實作細節，不該漏到 UI
重新整理歸零累加在前端 state，「這一輪 session」＝「我打開這頁到現在」

累加刻意做在前端：後端每次請求各自呼叫 query()、維持無狀態，前端本來就持有整段對話，天然是這一輪 session 的邊界持有者。詞彙定義見 CONTEXT.md。

9. 互動與無障礙備註

  • 顯示處理過程開關：純顯示濾鏡。關閉期間工具歷程照常收集，重新開啟後完整可見；刻意不做持久化。
  • 鍵盤：Enter 送出、Shift+Enter 換行；輸入法組字中的 Enter 為選字，不送出。
  • 狀態圖示：三種狀態圖示皆帶 aria-label（進行中／成功／失敗），不單靠顏色傳達語意。
  • 訊息語意：使用者與助手以位置（左／右）＋色塊／卡片雙重區分，非僅靠顏色。
  • 長字串：工具全名以 break-all 換行，避免窄欄溢出。
  • 用量數字：以 toLocaleString() 顯示千分位（如 11,604），長數字才讀得出量級。
